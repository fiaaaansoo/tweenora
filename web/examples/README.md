# web/examples/

Runnable examples of the `@tweenora/webgl2` package, one subfolder per API area
(P3-3b to P3-3g). Each example is an HTML page that loads the built package
(`web/rive-wasm/js/npm/webgl2/`) and publishes its state in
`window.twnoCheck` (`state`, `error`, `frames`, `instance`...) and in the tab
title, so that checks do not have to read pixels.

## Usage

```bash
bash web/build_webgl2_package.sh --no-wasm   # only if rive.js does not exist yet
python web/examples/prepare_assets.py        # copies the .riv files, produces the .twno files
python web/examples/serve.py                 # http://127.0.0.1:8765/
```

- `prepare_assets.py` copies the `.riv` files listed in `ASSET_SOURCES` to
  `web/examples/assets/` and writes their `.twno` there (`tools/twno_convert.py`). The
  sources are the original Tweenora examples (`docs/examples/`, versioned,
  generated by `tools/twno_gen/`) and the upstream test files
  (`runtime/tests/unit_tests/assets/`, `web/rive-wasm/js/test/assets/`). This output
  folder is ignored by git: no copy of an upstream file is versioned.
- `serve.py` serves `web/examples/` at the root, the package under `/pkg/` and the
  assets under `/assets/`, with `application/wasm` for `.wasm` files, no cache,
  and no way out of these three folders. The examples refer to them by
  absolute paths (`/pkg/rive.js`, `/assets/two_artboards.twno`).
- `serve.py --cors` adds `Access-Control-Allow-Origin: *`, `--cache` adds long-lived
  `immutable` cache headers (default: `no-store`); `docs/baseline/self-hosting-p3-4.md` gives the headers to serve.
- The pages take the file to load from `?file=`; a `.twno` and its equivalent
  `.riv` give the same rendering.

## Browser test mode

Decision (P3-3b): browser scenarios are run by the `playwright` MCP (already
installed, it drives the machine's Chrome) and not by `@playwright/test` in
this folder.

- No extra npm dependency and no extra browser to download: the repository
  has no `package.json` at the root and `web/rive-wasm/js` has its own.
- The pages expose `window.twnoCheck`: a scenario consists of opening a URL,
  waiting for `twnoCheck.state` (`drawing`, `error`...) and reading a few values.
  A replayable script can be rewritten as `@playwright/test` without changing the pages.
- Render comparison: one capture of the `#canvas` element per page, then a
  byte comparison of the two PNGs (two pixel-identical renders give the same file).
- What stays automatic and replayable without a browser: the Python tests in this
  folder (`python -I -m unittest discover -s web/examples/tests`) and those of the
  inventory (`node --test web/parity/api-inventory.test.mjs`), including a text
  check: the example of a row marked as demonstrated must name the member (the enumeration
  name for its values). It does not prove that the page exercises the member; the
  `playwright` scenarios do.
- P3-4 will also need to inspect network requests: the MCP does it
  (`browser_network_requests`).

## Contents

- `loading/`: loading and playing the file (P3-3b). `loading/index.html`
  lists the pages and their parameters.
- `state-machines/`: animations, state machines, inputs, events and
  pointers (P3-3c). `state-machines/index.html` lists the pages.
- `data-binding/`: view models, instances, bound values, lists, images, fonts and bound
  artboards (P3-3d). `data-binding/index.html` lists the pages.
- `text-layout/`: text runs, hosted and fallback fonts, responsive layout (P3-3e).
  `text-layout/index.html` lists the pages.
- `audio/`: embedded, nested and hosted audio, volume, `AudioContext` state (P3-3f).
  `audio/index.html` lists the pages; real listening is not scriptable.
- `scripting/`: files with Luau scripts, inputs through the view model (P3-3g); report:
  `docs/baseline/scripting-p3-3g.md`.
- `common.js`, `common.css`: shared published state and style.
- `tests/`: Python tests for the tooling.
